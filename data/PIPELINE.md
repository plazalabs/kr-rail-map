# 한국 철도 데이터 파이프라인 (PIPELINE.md)

> **출처 표기 (앱에 그대로 넣을 문구):**
> 노선/역 데이터 © OpenStreetMap contributors, ODbL 라이선스

## 1. 개요

- 목적: 한국 철도 노선도 웹앱이 읽는 `lines.geojson` / `stations.geojson` 생성
- 입력: Geofabrik 남한 OSM PBF → pyosmium 파싱 → GeoJSON 2종 출력
- 파이프라인 스크립트: `data/build_data.py` (재현: `cd data && python3 build_data.py`)
- 검증 스크립트: `data/verify.py` (스키마 검사 + 유명역 스팟체크)

## 3. 파서 설치

VM에 osmium/GDAL/shapely이 없어서 pyosmium을 사용 (manylinux wheel 제공, 컴파일 불필요):
```bash
pip install --break-system-packages osmium   # osmium 4.3.1 설치됨
```

시행착오 기록:
- 처음에 `osmium.index.create_map("dense_file_array", path)`로 전체 노드 위치 인덱스를 만들려 했으나,
  pyosmium 4.3.1의 `create_map`은 인자를 1개만 받고, dense_file_array는 최대 노드 ID 기준으로 파일이 커져서
  "No space left on device"로 실패 (OSM 노드 ID가 수십억 단위라 수십 GB 필요).
- 해결: 위치 인덱스를 쓰지 않고 3-pass 방식으로 변경.
  pass1: route relation 수집 → pass2: 멤버 way의 노드 ID만 수집 + 역 노드 수집 →
  pass3: 필요한 노드의 좌표만 dict에 적재 후 way geometry 생성.
  메모리 사용량 약 30 MB, 전체 실행 약 13분.

## 4. 추출 규칙 (build_data.py)

**노선 (lines)**
- `type=route` + `route ∈ {railway, subway, light_rail, monorail, tram, train}` relation 수집.
  - `route=train`은 스펙의 5개 값에 없지만, KTX/ITX-새마을/무궁화호 열차 운행계통 relation이
    이 값으로만 존재해서 포함 (chul.mom의 "기차 노선 보기"에 해당). 총 106개 중 포함.
- 제외: `railway=disused` / `disused=yes` / `abandoned=yes` 태그 (10개),
  이름에 `폐선` 포함 (1개: 구 동해선 태화강 이남 폐선),
  북한 노선 4개 (평부선, 금강산청년선, 금강산선, 구 경원선 — 위도 37.9~38.6, 휴전선 일대/이북).
- geometry: 멤버 way들의 좌표를 끝점 매칭으로 이어 붙이기 (greedy chaining).
  이어지지 않는 조각은 MultiLineString으로 유지 (62개 노선).
- `id`: `{network}-{ref}` 슬러그 우선, 없으면 `name:en` 슬러그, 없으면 `r{relation_id}`. 중복 시 `-2` 접미.
- `name_ko` = `name:ko` → `name`, `name_en` = `name:en` (없으면 null). 둘 다 없으면 스킵.
- `color` = relation의 `colour`/`color` 태그를 `#RRGGBB`로 정규화, 없으면 null.
- `category`:
  - `subway` → metro / `light_rail,monorail,tram` → urban
  - `route=train` + 이름에 고속/KTX/SRT → ktx, 그 외 train → conventional
  - `route=railway` + 이름에 고속 → ktx, 그 외 → conventional
- `status`: `state=proposed` → planned / `construction` 태그 또는 이름에 공사·예정·미개통 → construction / 그 외 open.

**역 (stations)**
- `railway=station` / `railway=halt` 인 노드 수집 (이름 없는 5개는 스킵).
- 노선 귀속: relation 멤버인 노드 → 해당 노선들 (65개 역).
  멤버십이 없으면 500m 이내 가장 가까운 노선 geometry에 폴백 귀속 (1,150개 역).
  500m 이내 노선이 없으면 미귀속 (121개 역).
- `id` = `st-{node_id}`, `line_id` = 첫 번째 노선 (없으면 null), `lines` = 노선 id 배열.

## 7. chul.mom 수치와 비교 (참고용)

| | chul.mom 표기 | 본 파이프라인 | 비고 |
|---|---|---|---|
| 한국 노선 | 302 | **336** | relation 단위 집계 |
| 한국 역 | 2,377 | **1,336** | 고유 노드 단위 집계 |

괴리 원인 분석:
- **노선 336 > 302**: OSM에 방향별·운행계통별 relation이 중복 등록되어 있음.
  예: 수도권 1호선 약 90개 변형(1-8~1-99), 수인·분당선 약 25개, 4호선 약 28개.
  chul.mom의 302는 중복을 제거하거나 다른 기준으로 집계한 것으로 보임 (추론).
  앱의 노선 목록 UX를 위해서는 물리 노선 단위 중복 제거가 후속 작업으로 필요 (§8 이슈 1).
- **역 1,336 < 2,377**: 본 파이프라인은 `railway=station/halt` 고유 노드만 집계.
  PBF 전체 태그 분포: `railway=station` 약 1,325개, `railway=halt` 16개,
  `railway=tram_stop` 6개, `public_transport=station`(railway 태그 없음) 518개.
  tram_stop(+6)과 pt=station(+518)을 다 합쳐도 1,860으로 2,377에 못 미침.
  chul.mom은 역-노선 쌍 단위 집계이거나 별도 데이터 소스를 쓰는 것으로 보임 (추론, 검증 불가).
  본 수치는 OSM 원시 데이터 기준이므로 그대로 사용하고, 앱에서 필요하면 pt=station 병합을 후속 검토.

## 9. 이슈 사항

1. **운행계통별 relation 중복**: 1호선 약 90개, 수인·분당선 약 25개, 4호선 약 28개 등
   방향·급행/특급 패턴마다 별도 relation. 앱 노선 목록에 그대로 노출하면 UX가 깨짐.
   후속 작업: `(network, ref)` 기준 대표 노선 선정 또는 앱에서 그룹핑.
2. **역-노선 귀속 품질**: relation 멤버십으로 귀속된 역이 65개에 불과하고 1,150개가 500m 근접 폴백.
   폴백은 단일 노선만 부여하므로 환승역의 `lines` 배열이 불완전함
   (서울역에 1호선·경의중앙선·공항철도가 안 붙는 식). OSM 데이터 자체의 한계.
   개선안: 동일 이름 역 노드들을 병합해 lines 배열을 채우는 후처리.
3. **미귀속 121개 역**: 관계 relation이 없는 구간의 역 (예: 정선, 대광리·신탄리(경원선 연천 이북),
   증평, 군산, 광천 등 지방 KORAIL역). 해당 구간 route relation이 OSM에 없음.
4. **노이즈 relation**: `운곡길`(도로 오태깅 의심), `일직터널`(터널 단일 구조물),
   `하이원추추파크 레일바이크`·`간현레일바이크`(관광용), `철도종합시험선로`,
   `송정리 비행장선`·`K-2인입선`(군용 인입선), `대구선`·`경전선` 중복 relation.
   원본 충실 원칙으로 일단 포함, 앱 노출 전 수동 필터 권장.
5. **name_en 공백**: 노선 29개, 역 21개에 영어 이름 없음 (null 유지, 지어내지 않음).
6. **금강산선·구 경원선 제외**: 휴전선 일대 구선(폐선)으로 북한 노선으로 분류해 제외.
   남한 구간(철원 일대) 표시가 필요하면 복원 가능.
7. **좌표 정밀도**: 소수점 6자리로 반올림 저장.
8. **GTX-C·8호선 연장 등 공사 중 노선**: OSM relation에 `construction` 태그가 있는 것은
   광주 2호선 2개뿐. GTX-C 같은 대형 프로젝트는 route relation 자체가 아직 없음.
   앱에서 "공사 중" 레이어를 보여주려면 별도 데이터 소스 필요.

# 부동산(주변 시세) 파이프라인

실거래가 → 역. 순서를 지켜야 한다. 2번은 1번이 만든 캐시를 쓰고, 3·4번은
2번이 만든 `_station_dong.json` 을 쓴다.

```bash
python data/lawd.py                      # 코드표 자체 점검 (키 불필요)
python data/fetch_rtms.py --metro --from 202604 --to 202609   # 1. 실거래가 (82개 시군구)
python data/build_station_dong.py        # 2. 역 ↔ 법정동 (RTMS 캐시로 시군구를 확정)
python data/build_station_price.py       # 3. 법정동 중위값 → station-price.json
python data/build_station_complex.py     # 4. 단지·평형대 → station-complex.json
python data/build_sources.py             # 5. 출처 표 갱신 (data.html)
```

### 세대수·공급면적은 K-apt 에서 온다 (선택 단계)

4번 앞에 끼어드는 단계다. 없어도 4번은 그대로 돌아간다 — 세대수가
안 붙을 뿐이다.

```bash
python data/fetch_kapt.py --probe        # 살아 있는 서비스 버전과 승인 여부
python data/fetch_kapt.py --all          # 목록 + 기본정보 → data/_kapt/units.json
python data/build_station_complex.py     # 4. 여기서 단지에 세대수·공급면적이 붙는다
```

**활용신청이 따로 필요하다.** 공공데이터포털에서 아래 둘을 신청한다
(자동승인, 즉시). 이용허락범위는 둘 다 "제한 없음"이다.

| 서비스 | 데이터셋 |
|---|---|
| 국토교통부_공동주택 단지 목록제공 서비스 | data.go.kr/data/15057332 |
| 국토교통부_공동주택 기본 정보제공 서비스 | data.go.kr/data/15058453 |

승인 전에 부르면 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR(30)` 이 온다.
이걸 "키가 틀렸다"로 오해하면 한참을 헤맨다. **12 와 30 은 다른 문제다.**

- `12 NO_OPENAPI_SERVICE_ERROR` = 그런 오퍼레이션이 없다 → **버전 번호**가 틀렸다
- `30 SERVICE_KEY_IS_NOT_REGISTERED` = 오퍼레이션은 있다 → **활용신청**을 안 했다

서비스 이름 뒤의 버전은 예고 없이 올라간다. 2026-10 기준 살아 있는 것은
`AptListService4` / `AptBasisInfoServiceV5` 인데, 흔히 도는 예제는 V2·V3 를
적고 있다. 그래서 `fetch_kapt.py` 는 1~8 을 훑어 살아 있는 것을 찾아
`data/_kapt/_endpoints.json` 에 적어 두고 다음부터는 그걸 쓴다.

**면적은 단지 평균이다.** 세대별 공급면적이 아니다.

**K-apt 는 공급면적을 주지 않는다.** 실제로 주는 면적은 셋뿐이다.

| 필드 | 뜻 | 쓰임 |
|---|---|---|
| `privArea` | 전용면적 합 | ÷세대수 = `ea` (평균 전용면적) |
| `kaptMarea` | **관리비부과면적** 합 | ÷세대수 = `ba` (평균 관리비부과면적) |
| `kaptTarea` | 연면적(계단·주차장 포함) | 쓰지 않는다 — 세대 면적이 아니다 |

관리비를 공급면적에 부과하는 단지가 대부분이라 `ba` 가 사실상 공급면적과
같아지지만, 전용면적에 부과하는 단지도 있다(관리비부과=전용, 전용률 100%).
그래서 이름을 바꾸지 않고 **관리비부과면적**이라고 적고, 화면에서만
`공급*` 로 표시한 뒤 각주로 밝힌다. `pr`(전용률)은 `ea÷ba` 로 계산한 추정값이다.

**세대수 필드는 `hoCnt` 다.** 흔한 예제가 적는 `kaptHoCnt` 는 존재하지
않는다. 이름을 잘못 짚으면 세대수가 통째로 빈다.

**평형 구성은 `kaptMparea60/85/135/136`** — 전용면적 구간별 세대수다
(~60 / 60~85 / 85~135 / 135~). 3,000세대라도 전부 59㎡면 성격이 전혀
다르므로 평균 하나보다 이쪽이 쓸모 있다.

합이 `hoCnt` 와 **정확히** 맞지는 않는다. 같은 세대를 두 방식으로 센 값이라
±1~3 은 실제로 어긋나고(5,301곳 중 61곳), 20% 넘게 벌어지는 단지도 있다
(광진코지웰 296 vs 364). 후자는 둘 중 하나가 틀렸다는 뜻이고 어느 쪽인지
알 수 없으므로 **구성만 버리고 세대수는 남긴다**(`plausible()`).

### 일일 한도(22)는 '없는 단지'가 아니다

개발계정은 하루 10,000회다. 84개 시군구 목록(10,231곳) + 기본정보 3,235곳을
재시도까지 하면 하루에 다 못 받는다. 한도를 넘으면 `LIMITED_NUMBER_OF_
SERVICE_REQUESTS_EXCEEDS_ERROR(22)` / HTTP 429 가 오는데, **응답이 0.1초 만에
돌아온다.** 이걸 `continue` 로 넘기면 1,009곳이 0.2초 만에 '없음'으로
처리되어 `basis.json` 이 완성된 것처럼 보인다 — 2026-10-28 에 실제로 그렇게
1,963곳을 잃었다. 그래서 22 는 재시도도 건너뛰기도 하지 않고 **즉시 멈춘다**
(`QUOTA_CODES`). 받은 것까지는 저장하고 종료코드 3 을 낸다.

다음 날 같은 명령을 다시 치면 이미 받은 단지는 건너뛰고 나머지만 받는다.

```bash
python data/fetch_kapt.py --basis    # 어제 못 받은 것부터 이어서
python data/build_station_complex.py
```

2026-10-28 현재 기본정보 **1,436 / 3,235** (한도로 중단). 단지 5,301곳 중
1,361곳(26%)에 값이 붙어 있다. 전부 받으면 45% 안팎이 된다 — 나머지는
K-apt 가 담지 않는 300세대 미만 단지이거나, 이름이 달라 짝을 못 지은 단지다.

### 04 HTTP_ERROR 는 '이 단지가 없다'가 아니다

2026-11-01 에 겪은 것. 같은 키로 실거래가(RTMS)는 0.2초에 정상 응답하는데
K-apt 두 서비스만 `returnReasonCode 04` / `errMsg: HTTP_ERROR` 를 0.4초 만에
돌려줬다. 버전 경로를 3·4·5 로 바꿔 봐도, 75초 쉬었다 다시 해도 같았다.
즉 **키 문제도, 요청 형식 문제도 아니다.** 서비스 장애이거나 이 서비스만의
한도 초과인데, 응답만 봐서는 둘을 구별할 수 없다.

구별할 수 없으면 **어느 쪽이든 멈추는 게 맞다.** 한 건 실패로 보고 계속 돌면
991곳 × 재시도 5회 × 4초 ≈ 6시간을 헛되이 돌고 나서 "받은 것 없음"만 남는다.
그래서 `DOWN_CODES = ("04", "05")` 가 `DOWN_STREAK = 5` 번 연달아 오면
`down_error()` 로 멈춘다. 간헐적으로 튕기는 경우(3건에 1번)는 그냥 넘어간다 —
`fetch_kapt --selftest` 가 두 경우를 다 잠근다(54개).

```bash
python data/fetch_kapt.py --basis    # 지금은 여기서 5건 만에 멈춘다
# → "중단: [04] 5건 연속 실패 — 서비스가 응답하지 않는 것으로 본다."
```

게이트: 1세대 전용 10~400㎡ · 관리비부과 10~500㎡ · 전용률 50~98% 를
벗어나면 **그 값만 버리고 세대수는 남긴다**. 틀린 면적을 보여주느니
안 보여주는 게 낫다.

**두 자료를 교차 확인한다** (`plausible()` + `build_station_complex.py`).

| 보는 것 | 왜 |
|---|---|
| `ba > ea` | 관리비를 전용면적으로 부과하는 단지는 `kaptMarea == privArea` 다. 그대로 두면 '전용 93㎡ · 공급 92㎡' 가 나온다 — 공급이 전용보다 작을 수 없다. 1,219곳 중 114곳. |
| 평형구성 합 ≈ `h` | ±2 또는 2% 를 넘으면 구성만 버린다 |
| `ea` vs 실거래 면적 | 2.5배 넘게 벌어지면 **이름이 다른 단지에 붙은 것**이다. '상봉생활'(전용 20㎡ 다세대)이 57.5㎡ 짜리 299세대 단지에 붙었다. 비교는 `rows[0]` 이 아니라 **화면에 나가는 중위값**으로 한다 — 60㎡·85㎡ 가 섞인 단지에서 `rows[0]` 이 60㎡ 면 통과해 버린다. |

### 응답은 JSON 이다 (XML 이 아니다)

두 서비스는 `_type=xml` 을 보내도 JSON 만 돌려준다. XML 파서만 두면 정상
응답을 "XML 이 아님"으로 판정해 **승인됐는데도 실패로 보고**한다.
`parse_payload()` 가 둘 다 받는다.

### 빈 응답을 성공으로 치지 않는다

폐기된 `AptListService1~3` 은 오류 대신 **빈 목록**을 돌려준다. "오류가
없다"만 보고 버전을 고르면 V1 에 붙어 `totalCount 0` 을 받는다. 실제로
그렇게 오해했다. `discover()` 는 **값이 실제로 있는 버전**만 고른다.

### 중간에 끊겨도 이어서 받는다

84개 시군구를 도는 중 게이트웨이가 `04 HTTP_ERROR` 를 한 번씩 뱉는다.
재시도(3회, 지수 백오프)로 대개 넘어가지만, 넘지 못해도 수집 전체를
죽이지 않도록 시군구 단위로 건너뛴다. 받은 것은 `data/_kapt/list_by_sgg.json`
· `basis.json` 에 5~200건마다 저장하므로 다음 실행이 이어서 한다
(`--refresh-list`, `--refresh-basis` 로 캐시를 버린다).

# 노선 선형을 OSM 으로 옮기는 파이프라인

상업적 재사용이 확인되지 않은 철도맘 화면을 보고 그린 선형을 OSM 선로에서 다시
계산한 것으로 바꾼다. 목적은 법적 안전이지 정확도 포기가 아니므로, **검증을
통과한 노선만** 바꾼다.

```
osm_pbf_extract.py            PBF → data/_osm/rail_ways.json, route_rels.json
  ↓
fetch_osm_alignments.py       route relation → 선형 후보  (방법: relation)
build_align_by_graph.py       역↔역을 선로 따라 최단경로 (방법: graph)
  ↓
apply_osm_alignments.py       두 후보를 검증해 lines.geojson 에 반영
```

## relation 방식이 안 되는 경우

OSM 에서 일반철도는 **운행 계통 relation** 으로만 있고 실제 선로는
`railway=rail` way 로 흩어져 있는 경우가 많다. KTX 경부선 relation 은 way 가
1개뿐이었다(1.8km). 그래서 선로 전체를 정점 그래프로 만들고 역과 역 사이를
최단경로로 잇는 방식을 같이 쓴다. 역 좌표는 OSM 역 노드와 1m 이내로 같으므로
그래프 방식이 역 이탈이 더 작다(중앙값 2~5m).

## 선로가 50m 쯤 끊겨 있을 때

터널 입·출구나 편집 경계에서 way 가 끊겨 있으면 경로가 없어서 12km 를 돌아가거나
직선을 긋게 된다. 경의선 효창공원앞~공덕이 그랬다. 15m 이내는 비용 2배로 잇고,
60m 까지는 **비용 6배**로 잇는다. 실제 선로가 있으면 6배짜리는 절대 선택되지
않으므로, 마지막 수단으로만 쓰인다.

## 반영 조건 (apply_osm_alignments.py)

1. 역의 90% 이상이 선에서 300m 안, 중앙 이탈 150m 이내
2. 역이 선에서 400m 넘게 떨어지는 곳이 없을 것
3. **직선으로 메운 구간이 한 곳도 없을 것** — 직선은 그 구간의 모양을 지어내는
   것이고, 양 끝 역을 반드시 지나므로 '역이 선 위에 있다' 검사까지 통과해 버린다
4. 선형 길이가 역 순서대로의 직선 합보다 짧지 않을 것 (삼각부등식)
5. 공식 영업거리가 있으면 ±8% 이내
6. **지금 선형과 길이가 15% 안에서 맞을 것** — 두 자료가 서로 독립이므로,
   어긋나면 어느 쪽이 틀렸는지 자동으로 알 수 없다. 중부내륙선 83km(지금 136km),
   장항선 114km(지금 155km)는 선로 그래프가 다른 선로로 질러간 경우였다

- **OSM 선로가 끊김**: 동해선 포항~삼척, 태백선 고한~갈래호, KTX 호남선 공주~강경

# 역 안 환승 도보 시간

지금은 환승 1회를 4분으로 고정해 쓴다. 그런데 신도림 1↔2 와 노원 4↔7 은 실제로
걷는 거리가 다르고, 4분을 똑같이 매기면 '환승이 적은 경로' 를 고르는 판단이
뒤집힌다. OSM 정차점 좌표로 승강장 사이 거리를 재서 역·노선쌍별 시간을 낸다.

```
osm_platform_extract.py    PBF → data/_osm/stops.json  (정차점 2,341개)
  ↓
build_transfer_times.py    → data/transfer-times.json  (143역 / 222쌍)
```

## relation → 우리 노선

relation 이름에서 계통 표기(`: A → B`)와 **끝에 붙는** 꼬리표만 뗀 뒤, 우리
노선 이름과 접두사로 맞춘다. 접두사 비교는 **긴 이름부터** 해야
'수도권 전철 1호선 경인' 이 '수도권 전철 1호선' 으로 잘리지 않는다.

`급행` 을 문자열 어디서든 지우면 `수도권 광역급행철도 A선` 이 `수도권 광역철도
A선` 이 되어 매칭에 실패한다. 실제로 그렇게 만들었다가 4개 노선이 통째로
빠졌다. 접미사만 뗀다.

317개 중 312개가 붙고, 못 붙는 5개는 이름이 없는 relation 이거나 화물선·비행장선이다.

## 승강장 거리는 '최소 조합' 으로 잰다

**역 중심에서 가장 가까운 정차점**을 고르면 안 된다. 동대문은 1호선이 중심에서
62m, 4호선이 219m 지점에 있어서 그 둘을 비교하면 280m(6분)가 나오는데, 실제로는
1호선 141m 지점과 4호선 219m 지점이 마주 보고 있어 94m(3분)다. 승강장은 길어서
'중심에서 가까운 끝' 끼리 비교하면 거리가 부풀려진다. 정차점끼리 **모든 조합의
최소값**을 쓴다.

이름이 다른 정차점은 뺀다 — 동대문 반경 450m 에 동묘앞 정차점이 들어온다.

## 계산식

    환승 시간 = 수평거리 / 1.0 m/s + 90초   (2~12분으로 자름)

1.0m/s 는 계단·혼잡을 감안한 역내 속도다(지상 1.3m/s). 90초는 수직 이동·개찰·대기.
**지하 깊이 차이는 수평거리에 나타나지 않으므로** 고정값으로 보정한다. 공식
환승 소요시간 자료가 아니라 추정값이고, ±1분 정도 오차가 있다.

## 커버리지가 절반인 이유

265곳 중 143곳. 나머지 122곳은 정차점이 **양쪽 다** 있는 노선쌍이 하나도 없다.

- **미개통 노선**: GTX-D~H, 동북선, 동부선, 대전·광주 2호선 — OSM 에 정차점이
  없는 게 정상이다. 개통 전에는 환승할 수 없으니 4분 기본값이 맞다.
- **경부선·KTX**: 정차점이 일부 역에만 있다. 역 전체를 버리지 않고 **쌍 단위**로
  판단해서, 서울역처럼 다른 쌍은 잴 수 있는 역까지 사라지지 않게 했다.

## 검증

`tests/transfer.test.js` (23개)
- 자료 정합성: 역 id 존재, 그 역에 다니는 노선인지, 시간이 clamp 범위 안인지,
  거리↔시간이 계산식과 맞는지
- 알려진 값 대조: 동대문 3 / 잠실 4 / 사당 3 / 김포공항 2 / 종로3가 6 (±1분)
- 순서 검사: 동대문(1↔4) < 잠실(2↔8). 뒤집히면 '짧은 환승' 판단이 반대가 된다
- route.js 연동: 자료 없으면 4분, 있으면 그 값, 노선 순서를 바꿔도 같은 값

# 노선·역 목록을 미래철도DB에서 떼어내기

## 왜 떼어내나

미래철도DB(FRDB)는 스스로 **"비영리, 비상업, 비회원제, 무료, 개인 사이트"** 라고
밝힌다. 이용허락(라이선스) 표시는 없고, 첫 화면에 이렇게도 적혀 있다.

> 중요한 목적(부동산 투자, 이사, 언론기사화 등)으로 본 페이지의 정보를 이용하려는
> 분들은 관계당국을 통하여 다시 한번 정보를 확인하시기 바랍니다.

우리 목적이 정확히 그것이다. '공개돼 있다' 와 '자유롭게 쓸 수 있다' 는 다르다.
라이선스 표시가 없으면 저작권법 기본값은 **모든 권리 유보**이고, 사실을 상당한
노력으로 모은 데이터베이스는 별도로 보호된다(저작권법 제91조 이하). 노선 84개와
역 1,247개를 통째로 옮긴 것은 '상당 부분 복제' 에 해당할 수 있다.

## 어떻게 대체하나

같은 사실을 **독립된 세 자료**에서 다시 얻어 대조한다. 셋 중 하나라도 확인해주면
그 (노선, 역) 쌍은 확인된 것으로 본다.

| 방법 | 자료 | 라이선스 | 범위 |
|---|---|---|---|
| `official` | 공공데이터포털 국가철도공단 노선별 역위치 CSV | 이용허락범위 제한 없음 | 19개 노선 682행 |
| `osm-relation` | OSM 노선 relation 의 정차점 | ODbL | 51개 노선 |
| `osm-geometry` | OSM 역 노드가 선형 300m 안에 있는지 | ODbL | 선형이 있는 모든 노선 |

```
official_stations.py          공식 CSV → {노선: {역명, 좌표, 운영기관}}
build_membership.py           위 셋 + 우리 데이터 → data/line-membership.json
verify_osm_membership.py      OSM 만으로 대조한 보고서 (읽기 전용 점검)
relabel_plan_sources.py       frdb_* 속성 제거 + 계획 노선 provisional 표시
```

## 계획 노선은 provisional

개통 전 10개 노선(GTX-B~H, 동북선, 동부선, 광주 2호선)은 OSM 에도 공식 파일에도 없다.
`lines.geojson` 에 `provisional: true` 와 `plan_source` 를 붙였다. 역명은 계획 발표
기준이라 확정이 아니고, 화면에서도 그렇게 적는다.

`provisional`(아직 안 지어짐)과 `partial`(지어졌는데 일부 역이 미확인)을 섞으면 안 된다.
섞으면 '미개통 노선' 과 '일부가 미확인인 개통 노선' 을 구별할 수 없게 된다.

## 임계값을 풀지 않는다

확인율 90% 미만인 노선이 생기면 테스트가 실패한다. 예외는 `KNOWN_GAPS` 에
**이유를 적은 노선만** 이다. 임계값을 통째로 낮추면 다음에 생기는 진짜 누락도
같이 통과해 버린다.

`tests/membership.test.js` (22개) 가 잠그는 것:
- 증빙 파일의 역 수가 지금 데이터와 같은지 (데이터를 고치고 증빙을 안 고치면 실패)
- `unconfirmed` 에 적힌 이름이 그 노선에 실제로 있는 역인지
- 개통 노선 확인율 98% 이상, 90% 미만은 이유가 있어야 함
- `provisional` 이 노선 데이터와 증빙에서 같은지
- `sources.json` 에 frdb 가 다시 들어오지 않았는지, `not_used` 에 이유가 있는지

# 도심 접근성 (access.json)

`node data/build_access.js` → `data/access.json`

역에서 5개 거점(도심·광화문 / 여의도 / 강남 / 서울역 / 판교)까지의 최단 소요시간을
`now`(운행 중 노선만)와 `after`(착공·계획·구상 포함) 두 벌로 계산한다.
1,246역 × 2회 다익스트라 ≈ 70초.

## 시간 모델은 route.js 하나만 쓴다

빌드 스크립트가 `js/route.js` 를 vm 으로 불러 `RouteFinder.allTimesFrom()` 을 쓴다.
여기서 시간 계산을 따로 구현하면 상세 패널의 "강남까지 34분" 과 길찾기 탭의 34분이
갈라진다. 예전에 `route-compare.js` 가 그래서 갈라졌다.

`tests/access.test.js` 가 표본 24역 × 5거점을 **다시 계산해 파일과 대조**한다.
선형·역·환승시간을 고치고 `build_access.js` 를 안 돌리면 여기서 실패한다.

## 표정속도는 노선별로 둔다

예전에는 카테고리 하나(`metro: 32`)로 묶었다. 그래서 춘천→서울이 172분(실제 78분)으로
나왔다. 경춘선(표정 62km/h)과 2호선(44km/h)이 같은 상수였기 때문이다.
지금은 `LINE_SPEEDS` 에 영업거리÷소요시간으로 구한 값을 노선별로 적는다.

`tests/access.test.js` 가 공표 소요시간 11쌍을 ±45% 로 잠근다. 현재 최대 오차 26%
(춘천→서울). 이 테스트가 깨지면 표정속도 표가 망가진 것이다.

## 한계

- 116역은 선형이 없어 계산에서 빠진다 (경전선 32 · 태백선 21 · 장항선 18 등).
  지방 일반철도 선형이 아직 개략선이라 역이 선형에서 1.5km 넘게 떨어진다.
  화면에서는 "계산하지 못했습니다" 로 밝힌다. 0분으로 보이면 안 된다.

- 노선당 표정속도 하나라 급행/완행 구간 차이를 못 담는다. 신분당 정자~강남처럼

## 키는 서비스마다 따로다

국토교통부_건축HUB_주택인허가정보 — <https://www.data.go.kr/data/15136560/openapi.do>

공공데이터포털은 **서비스마다 활용신청을 따로** 받는다. 실거래가(RTMS)가 잘 되는

"이 서비스에 이 키가 등록되지 않음"이다. 절대 빈 결과로 넘기면 안 된다 —
그렇게 넘겼다면 "역 주변에 공급 물량이 없다"는 거짓 보고가 나간다.

키는 `data/.secrets.json` 에 `data_go_kr_dev` 로 따로 둔다. 공용 키(`data_go_kr`)를
덮어쓰면 실거래가 파이프라인이 조용히 죽는다.

`fetch_dev.py` 는 30 을 받으면 안내를 띄우고 멈춘다. 22(일일 한도)도 재시도하지 않는다.

## 법정동 코드 없이는 아무것도 안 준다

`sigunguCd` 만 넘기면 `{"body":{}}` — HTTP 200 에 알맹이가 없다. **`bjdongCd` 가
필수**다(2026-11-01 실측). 그래서 수집은 처음부터 법정동 단위로 돈다.

코드표는 두 자료를 합친다 (`fetch_dev.py` 의 `bjdongs_of()`).

1. **K-apt 단지 목록** (`_kapt/list.json`) — 단지가 있는 동. 역이 `부발읍` 처럼
   읍/면까지만 적혀 있어도 그 아래 리를 넓게 덮는다.
2. **법정동코드 전체자료** (`data/_gov/bjd_codes.json`) — 역 주소의 동 이름으로
   찾은 코드.

2번이 없으면 **단지가 없는 동네를 영영 못 받는다.** 1번만 쓸 때는 역이 있는
376쌍 중 285쌍(76%)만 코드를 알았다. 종로1~6가·을지로1~7가 같은 도심 소규모
지역은 K-apt 에 단지가 없어서 코드를 알 길이 없었다. 2번을 붙여 **376쌍 전부**를
찾는다. 받는 법정동은 845곳 → **1,191곳**이 됐다.

데이터가 없는 법정동은 **HTTP 200 + 본문 0바이트**로 온다. 빈 본문을 파서에
그대로 넣으면 ParseError 로 순회가 통째로 죽는다 — 한 곳이 비었다고
전체를 잃지 않도록 0건으로 처리한다.

## 법정동코드 전체자료 (`bjd_codes.py`)

행정표준코드관리시스템이 법정동코드 전체자료를 내려준다. ZIP 안에 cp949 탭 구분
3열(`법정동코드 / 법정동명 / 폐지여부`)로 53,403줄. 존재하는 법정동만 접어
`data/_gov/bjd_codes.json` (561KB, 법정동 20,276곳 · 시군구 256곳)으로 커밋한다.

```
POST https://www.code.go.kr/etc/codeFullDown.do
  Referer: https://www.code.go.kr/stdcode/regCodeL.do
  codeseId=법정동코드&chkHigh=0&chkLow=0&chkSd=0&chkSgg=0&chkUmd=0&chkRi=0&chkJijuk=0
python data/bjd_codes.py --build <원본경로>   # json 다시 만들기
python data/bjd_codes.py --check              # 커밋된 표가 원본과 같은지
```

**원본은 커밋하지 않는다.** `--check` 가 원본과 대조하므로, 표를 손으로 고치면
들킨다.

### 이름을 자르는 방법 — 낱말 수로 자르면 틀린다

이름에서 시군구 접두사를 **글자 그대로 걷어낸다**(`세종특별자치시 연서면 용암리`
→ `연서면 용암리`). 앞 두 낱말을 버리는 방식은 세종에서 깨진다 — 세종은 구가
없어서 읍/면 이름이 사라지고, 같은 이름의 리끼리 덮인다(실측 5건).

같은 이유로 키를 마지막 낱말(리)만 쓰면 **322줄이 조용히 사라진다**
(순천시 승주읍 봉덕리 vs 황전면 봉덕리). 그래서 `읍면 리` 전체를 키로 쓴다.
이름이 시군구 안에서 유일하지 않으면 `code_for()` 는 **None 을 준다** —
아무거나 집으면 남의 동네 인허가가 그 역에 붙는다.

### 인천 서구는 서해구·검단구로 갈라졌다 (확인)

`lawd.py` 가 "검단이 구로 승격된 것으로 보이지만 이름을 확인하지 못했다"고
적어 둔 것을 전체자료로 확인했다 — **28275 = 서해구, 28290 = 검단구.**

역 주소는 아직 `인천광역시 서구 불로동` 이라 28275 로 들어온다. 그런데 불로동은
이제 28290 에만 있다. 옛 코드로 조회하면 **없는 동을 조회해서 0건**이 온다.
`SGG_ALIASES` 가 28275 → [28275, 28290] 순으로 찾고, **돌려주는 코드의
시군구를 쓴다.** 이걸 놓쳐서 검단 7개 동(불로·마전·백석·오류·왕길·원당·당하)이
통째로 비어 있었다.

### 주소데이터의 오타·옛 이름

| 원본 | 실제 | 왜 |
|---|---|---|
| 구로구 `개보동` | `개봉동` | 국가철도공단 주소데이터 오타 (1호선 개봉역) |
| 파주시 `교하읍 야당리` | `야당동` | 교하읍이 동으로 승격 (경의중앙선 운정역) |
| 여주시 `능서면` | `세종대왕면` | 면 이름 개칭 (경강선 세종대왕릉역) |

`DONG_ALIASES` 에 적어 둔다. **코드만 고치면 절반이다** — 인허가는 받아 놓고도
이름이 달라서 역에 안 붙는다. `build_station_dev.py` 가 역 표를 만들 때
`code_for()` 로 이름과 시군구를 함께 맞춘다(실측 14개 역).


## 착공 여부는 이 자료로 알 수 없다 (설계를 한 번 뒤집었다)

처음엔 `stcnsDay`(실제 착공일)로 '확정/계획'을 나눠 내려 했다. 실제로 돌려 보니
**미래 물량 880건 전부가 '미착공'으로 나왔다.** 이유는 채움률이다.

| | 실제 착공일(`stcnsDay`)이 있는 비율 |
|---|---|
| 준공된 건 3,940 | **89%** |
| 아직 준공 안 된 건 3,523 | **2%** |

착공일은 준공 처리할 때 같이 적는 칸이라, 공사 중인 건은 비어 있다. 이걸로
'확정/계획'을 나누면 멀쩡한 공사 중 단지까지 "아무것도 확정되지 않았다"로
보여준다. 그래서 그 구분은 버렸다.

대신 **착공예정일이 이미 지난 물량**(`overdue`)을 낸다. 이건 사실이다 —
예정일이 지났는데 준공도 안 됐다는 뜻이고, 공사 중이거나 밀린 것이다.
노량진동 9,114세대 중 8,387세대가 여기 해당한다.

## 사업이 아니라 인허가 건이 온다

같은 대지·같은 세대수·같은 이름인데 관리번호만 다른 줄이 흔하다. 그대로 더하면
물량이 두 배가 된다(실측: 7,463줄 중 915줄, 미래 물량의 4.5%).

`dedupe()` 가 **이름·세대수·대지위치가 모두 같을 때만** 접고, 그중 가장 최근에
만들어진 줄(`crtnDay`)을 남긴다 — 일정이 바뀌면 새 승인 건이 생기므로 최신 줄이
지금 유효한 일정이다. **연면적은 키에 넣지 않는다.** 같은 사업의 승인 건끼리
81,297 과 81,065 처럼 0.3% 만 다른 경우가 있어서 넣으면 중복이 그대로 남는다.

넓게 접지는 않는다. '쌍용2단지 919세대' 와 '쌍용2단지 203동 136세대' 는 세대수가
달라서 다른 줄로 남긴다. 접으면 919세대짜리 단지가 136세대가 된다.

## '미정' 은 이름이 아니다

이 API 는 단지명을 모를 때 `bldNm` 에 `"미정"` 을 넣어 준다. 그대로 두면 화면에
'미정 1,499세대' 가 뜬다. `name_of()` 가 대지위치에서 '동 + 번지' 를 만들어
대신한다 — '노량진동 294-220번지 1,499세대' 가 '미정' 보다 훨씬 쓸모 있다.

## 날짜의 9999 는 '미정' 이다

준공예정일을 모를 때 `99991201` 이 온다. 그대로 쓰면 9,999년 입주 물량이 생긴다.
`ymd()` 가 1900~2100 밖을 버린다.

## 법정동은 대지위치 문자열에서 뽑는다

이 API 는 좌표를 주지 않는다. `platPlc`(대지위치)와 법정동 코드뿐이다.
`dong_of()` 가 `서울특별시 강남구 역삼동 123-4 외 2필지` → `역삼동` 으로 자른다.

- 시/구/군 으로 끝나는 토큰은 건너뛴다. `강남구` 를 법정동으로 잡으면 안 된다.
- **법정동 이름은 낱말 하나(읍/면이면 둘)다.** 그 뒤를 계속 붙이면 안 된다 —
  이 API 는 번지가 없을 때 대지위치를 `서울특별시 중랑구 면목동 블록` 으로
  적어 보낸다(**7,347줄 중 1,011줄**). 처음엔 번지가 나올 때까지 토큰을 모아서
  `면목동 블록` 이라는 이름을 만들었다. 그 이름은 어느 역과도 안 맞아서 물량이
  통째로 사라졌고, `불로동 블록` 이 9,735세대를 들고 1위에 올라 있었다.
  지금은 동/리 토큰에서 끊는다.
- 못 뽑으면 `bjd_codes.json` 의 (시군구, 법정동 5자리) → 동 이름 표로 대신한다.
  그래도 없으면 버리고 몇 건인지 출력한다. 지어내지 않는다.

역과 잇는 것은 `dong_match.stations_in()` — 시세 파이프라인과 같은 함수다.
표기가 달라도(`부발읍` ↔ `부발읍 아리미`) 붙게 하려고 그 함수가 있다.

## 역이 여러 법정동에 걸칠 때

한 역이 두 법정동에 걸치면 양쪽 물량을 **더한다.** 그래서 같은 건이 두 역에
세어질 수 있다. 역별 값의 뜻은 "그 역이 속한 동네의 물량"이지 "역 반경 500m"가
아니다. 화면에서도 그렇게 적는다.

- `fetch_dev.py --selftest` 30개 — 오류 봉투(JSON/XML), 빈 본문·깨진 XML,

- `build_station_dev.py --selftest` 24개 — 대지위치 자르기(번지·'외 N필지'),
  미준공/최근준공 분리, 중복 승인 건 접기, 목록 상한, 이름 없는 건도 세는지

- `build_station_dev.py` 는 `_dev/rows.json` 이 없으면 **파일을 만들지 않고 멈춘다.**
