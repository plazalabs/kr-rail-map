# WORKFLOW.md · 시간을 아끼는 작업 방식 (Claude Code CLI)

## 1. 무엇이 문제였나

4일 동안 89개 노선, 실거래 7종, 길찾기 엔진까지 만든 건 큰 성과다. 문제는 **기능을 못 만든 게 아니라, 확인 장치 없이 덧붙인 것**이다.

### 정반합(AI 4개 피드백 순환)이 원인인가?
절반은 맞다. 정반합 자체보다 **"합"을 코드에 그대로 쌓은 것**이 문제였다. 화면과 코드에 증거가 남아 있다.

- **고르지 않고 둘 다 남긴 흔적**: 슬로건 2개, 투자 모드 버튼 3곳, 순위 기준 675역/696역.
- **피드백 한 건 = 국소 패치 한 건**: 코드 주석에 "(종합피드백 12장 B, 2026-11-14)", "(H7, 2026-11-14)", "(J3, …)", "2026-11-13 바로잡음".
- **같은 숫자를 기능마다 따로 계산**: 역 수 1,249 / 1,208 / 1,237 / 1,175 / 1,245.
- **보이지 않는 의존성**: 퀴즈가 투자 모드에서만 불러오는 시세 데이터에 기대서, 첫 방문자에게 0곳을 낸다.
- **검증 없는 리뷰**: AI 리뷰어는 화면 설명·코드를 읽고 의견을 낸다. 실제로 서울역 시세 탭과 개발 탭의 법정동을 대조하는 리뷰어는 없었다. 의견은 쌓이고 검증은 0.
- **긴 세션의 망각**: 4일짜리 세션은 여러 번 압축된다. 앞의 결정을 잊고 같은 걸 또 만든다.

### 데이터 파일을 열어 보고 확인한 실제 원인 (2026-11-16)

| 화면 증상 | 데이터 속 원인 |
|---|---|
| 역 수 1,249 vs 1,208 | `stations.geojson` feature 1,249개, **역 이름 고유 개수가 1,208**. 철도망 통계가 이름으로 셈 |
| 역 상세 "전국 1,237역" | `access.json`·`rank.json` 에 **12역 누락**(정선선 6, 인천공항 셔틀 3, 광주 2호선 2, 태백선 송학) |
| 서울역 GTX-A 인접역 "수서 ← 현재역" | GTX-A `stops` 가 두 운행 구간을 **한 줄로 이어 붙임**(…연신내→서울→수서→성남…) |
| 신사역에 은평구 시세 | 동 이름만으로 매칭. 같은 방식으로 **장신대→광진구 광장동(약 300km)**, **현충원(대전)→동작구 동작동(약 131km)** 도 오매칭 |
| 서울역 시세=동자동, 개발=남대문로5가 | 시세 파일과 개발 파일이 **각자 법정동을 고름**. 이런 역이 7개(공덕·시청·동대문·모란·신내·부발 포함) |
| 타임라인 GTX-C "미정" vs 랭킹 "2031" | 개통 연도가 `lines.geojson` 자유 문장(`opened: "2031년 목표 …"`)과 `rank.json` `year_lines` **두 곳에 따로** 있음. 타임라인 파서가 문장을 못 읽음 |
| 서울역 평당 4,601만원(4건) | 앱 스스로 "5건 미만은 값을 내지 않는다"고 써 놓고 대표값엔 적용 안 함. 이런 역 18개(홍대입구 1건 등) |
| (새로 발견) 개통 후 더 느려지는 역 | GTX-A 북쪽 24역(일산·운정·킨텍스 등)이 개통 후 1~2분 느려짐. 창릉 정차 추가 때문으로 보이며, 화면이 이걸 어떻게 보여 주는지는 미확인 |

**공통점: 모두 "같은 사실을 두 곳 이상에 적어 둔 것"에서 나왔다.** 테스트 한 줄이면 첫날 잡혔다.

## 2. 앞으로의 작업 방식

### 원칙 한 줄
**AI 4개 정반합보다 AI 1개 + 자동 테스트 + 사람의 최종 결정**이 훨씬 빠르다.

### ① 코드 전에 한 쪽짜리 기획 (30분)
- `docs/PRODUCT.md`: 핵심 흐름 하나와 **"안 만들 것"** 목록.
- 피드백이 범위 밖이면 다음 버전으로 보낸다.

### ② 데이터와 화면 분리
- 데이터 가공은 `scripts/` 에서 한 번만 하고, 결과는 `data/` 에 둔다.
- `js/` 는 숫자를 **읽기만** 한다. 다시 세거나 하드코딩하지 않는다.

### ③ 불변식 테스트가 시간 절약의 핵심
- `tests/data/invariants.test.mjs`: data 파일만 검사, 수 초. **지금 실제 데이터로 돌리면 19개 중 13개 실패**(=검수에서 찾은 문제들).
- `tests/e2e/invariants.spec.mjs`: 검수 때 손으로 한 화면 대조를 Playwright 로 옮긴 초안.
- 목록과 현재 상태: `docs/INVARIANTS.md`.

### ④ Claude Code 설정 (이 키트에 들어 있음)
| 장치 | 파일 | 하는 일 |
|---|---|---|
| 규칙 | `CLAUDE.md` | 숫자는 한 곳에서, 테스트가 완료 기준, 날짜 주석 금지 등 |
| Stop 훅 | `.claude/settings.json`, `.claude/hooks/stop-check.mjs` | Claude 가 "다 했어요" 하기 직전에 데이터 테스트 실행. 기준선보다 실패가 늘면 멈추지 못하고 다시 고친다 |
| 수정 금지 | `.claude/settings.json` permissions.deny | 불변식 테스트·기준선 파일을 Claude 가 못 고친다 (테스트를 바꿔서 통과시키는 것 방지) |
| 검수 에이전트 | `.claude/agents/data-auditor.md` | 외부 AI 4개 대신. 재현 가능한 불일치만 보고 |
| `/audit` | `.claude/commands/audit.md` | 테스트 전부 + 대조표 |
| `/fix-bug` | `.claude/commands/fix-bug.md` | 실패 테스트 먼저 → 최소 수정 → 전체 테스트 → CHANGELOG |
| `/triage` | `.claude/commands/triage.md` | 피드백을 버그/의견/범위 밖/틀린 지적으로 분류, 코드는 안 건드림 |

그 외 습관:
- **Plan mode(Shift+Tab)**: 큰 변경은 계획부터 받고 승인 후 실행.
- **작업 하나 = 커밋 하나**, 끝나면 `/clear`. 긴 세션 망각 방지.

### ⑤ 피드백 받는 방식 (정반합 대체)
1. AI 4개 피드백은 `feedback/` 에 **모으기만** 한다. 작업 Claude 에게 바로 넘기지 않는다.
2. `/triage` 로 분류: 버그 / 의견 / 범위 밖 / 틀린 지적.
3. 버그만 → 실패 테스트 → `/fix-bug`.
4. 의견은 **사람이 하나만 고른다. 합치지 않는다.**
5. 한 라운드 최대 5건. 테스트가 기준선 이하일 때만 다음 라운드.
6. 리뷰어에게는 "의견 말고 재현 절차가 있는 문제만"이라고 요청한다(`docs/FEEDBACK-TRIAGE.md`).

## 3. 지금 이 앱에 적용하는 순서

### 0일차 (1시간): 설치
1. 키트 파일을 저장소 루트에 복사 (README 참고).
2. `node --test tests/data/` → 실패 13개 확인.
3. `node .claude/hooks/stop-check.mjs --update-baseline` → 기준선 13개.
4. `npm i -D @playwright/test http-server` → `npx playwright install chromium` → `npx playwright test`.
   - 처음엔 **선택자 오류**(테스트 쪽 문제)와 **값 불일치**(앱 버그)가 섞여 나온다. 선택자 오류부터 테스트를 고친다(사람이, 또는 deny 를 잠시 풀고).

## 4. 한 줄 요약
4일 중 상당 부분은 서로 모순되는 의견을 합치는 데 쓰였다. 테스트가 있었다면 그 시간이 다 버그 잡는 데 쓰였을 것이다. **사실은 한 곳에만 적고, 테스트가 그걸 지키게 하고, 고르는 건 사람이 한다.**
